# 原稿から始める

ルールは [AGENTS.md](../../../AGENTS.md) に従う。ユーザーは自分の原稿を持っていて、それを補強する先行研究を求めている。**1 本の原稿に、サーベイとレポートは 1 本。** レポートのどこに力を入れるかは、原稿の状態による。

| 原稿 | 力を入れるところ |
| :--- | :--- |
| 書きかけ（節が無い・見出しだけ・薄い・引用が無い、作者の印 `[cite]`・`[@?]`・`TODO(priorwork): …`） | 欠けの地図（3 章）、補完の一覧（5 章） |
| 分析まで済んで、イントロ・先行研究・理論と仮説がまだ | 補完の一覧（5 章）。その部分を「節を書く」項目にする |
| 出来上がっている | 引用の点検（6 章）、足りない先行研究（7 章）、論の組み立て（9 章） |

頼まれていない節には「対象外」と書く。**原稿は読むだけで、書き換えない。** 直したほうがよい点は、レポートと報告で伝える。

前の版で作ったサーベイは、レポートの形が違う（`./priorwork status <survey> --json` の `purpose` が `draft` か `advice`）。そのレポートの見出しと `<!-- 書く内容: … -->` に従って続ける。残りが要るなら、新しいサーベイを作り、採用論文を `add` で登録する。

## 1. 原稿を読む

原稿は、ワークスペースの `manuscripts/<論文名>/` に置く決まり（`manuscripts/README.md`）。フォルダには原稿と、原稿に入っていない結果の表・図・ログが入っていることがある。**フォルダの中のファイルをすべて読む。**

- どの原稿か分からなければ、`manuscripts/` の中を見て、1 つならそれ、複数なら聞く。
- `manuscripts/` に無ければ、そこに置いてもらう（外のファイルを勝手に写さない）。
- 形式は問わない。`./priorwork read` でテキストにして読む（Markdown・Quarto（.qmd）・LaTeX・HTML（Quarto が書き出したものなど）・Word（.docx）・PDF。フォルダならすべてのファイルを順に出す。図はファイル名だけ）。

  ```bash
  ./priorwork read manuscripts/<論文名>
  ./priorwork read manuscripts/<論文名> --out /tmp/<論文名>.txt   # 長いときは書き出して分けて読む
  ```

- サーベイを作った後に読み直すときは、`--for <survey>` を付ける（`./priorwork read manuscripts/<論文名> --for <survey>`）。今の原稿を読んだと記録され、その後にユーザーが原稿を直すと、`./priorwork status` の次にやることに「原稿が変わった」と出る。そう出たら読み直し、何が変わったかをユーザーに伝えて、古くなったところ（欠けの地図と補完の一覧・下書き・助言。新しい主張に文献が要れば検索も）を直す。
- **Octavo のプロジェクト**（別のリポジトリ。`octavo.config.py` がある）の原稿は、`manuscripts/` に写さず、その場所を指す（例: `../make_or_buy/papers/main`）。`./priorwork read` は、原稿のほかにプロジェクトの分析の結果（`results/*.json`）・表・分析（`.qmd`）・図の名前と、原稿が引いている文献（`.bib` の `[@key]`）も出す。下の「Octavo のプロジェクトの原稿」も守る。

## 2. 何を作るかを相談して決める

原稿を読んだら、次を提案して**ユーザーの答えを待つ**（進め方によらない。依頼ですべてはっきりしているときだけ、待たずに進めて、報告でどう決めたかを伝える）。

- **力を入れるところ**: 上の表から、原稿の状態に基づく理由とともに。
- **対象**: 原稿のどこを対象にするか（例: 「2 章の先行研究と 3 章の仮説」「論文全体」）。
- **検索の範囲**: リサーチクエスチョン（原稿のもの）、分野、期間、採用・除外の基準、深さ（既定は full）。

答えを受けたらサーベイを作る。**同じ原稿に 2 本目のサーベイを作らない。** 今あるサーベイに足す。

```bash
./priorwork new "<テーマ>" --slug <slug> --by "<自分のモデル名>" --manuscript manuscripts/<論文名> --mode standard|auto|manual --depth full --question "..." --fields "..." --inclusion "..." --exclusion "..."
```

原稿が Octavo のプロジェクトにあれば、`new` がプロジェクトの Zotero のコレクションをサーベイに結び付ける（`./priorwork status <survey>` に「Octavo のプロジェクト」と出る）。

ここでの相談が、標準の進め方の 1 か所目の止まる場所（範囲）にあたる。以後は AGENTS.md「進め方」のとおり（標準なら、次はカードの記入の前で止まる）。

## 3. 原稿の要約を書く

レポートの 1 章を、原稿に書かれていることだけで埋める。推定値は原稿の表の値そのままにする。対象にする部分も書く。

## 4. 文献が必要な点を洗い出す

- **3 章**: 原稿の節ごとの状態（書けている / 薄い / 見出しだけ / 無い）と、作者の印（`./priorwork read` の最後）と、補う方針。作者の印は、作者がそこに文献を求めている印なので、すべて載せる。
- **4 章**: 文献で支える主張を ID（C1, C2, …）つきで。少なくとも次の種類を考える。

| 種類 | 原稿で使う場所 | 例 |
| :--- | :--- | :--- |
| 問題の重要性・パズル | イントロ | 「最低賃金の雇用効果は政策上の争点である」 |
| 貢献する研究の流れ（2〜4 本） | 先行研究 | 「地域間の比較による推定の系譜」 |
| メカニズム・理論 | 理論と仮説 | 「独占的買い手（モノプソニー）なら雇用は減らない」 |
| 対立する理論・知見 | 理論と仮説・考察 | 「競争的な労働市場なら雇用は減る」 |
| 方法・データの先例 | データと方法（補強） | 「同じ識別戦略・同じデータを使った研究」 |

  **主な結果のそれぞれについて、それと食い違う知見も主張として立てる**（「C3: X は Y を増やさないという報告がある」のように）。支える文献だけを集めない。
- **6 章**: 原稿が先行研究を引いている主な箇所を ID（R1, R2, …）つきで（原稿の場所・原稿の記述・引かれた文献）。
- **7 章**: 原稿の問い・理論・方法・結果のそれぞれについて、触れられていない研究の流れ。

## 5. 検索・選別する

`priorwork-new` の 2（検索）、`priorwork-screen`（選別）、`priorwork-snowball`（引用の追跡）の手順で進める。サブテーマの代わりに、4 の主張（C）や引用の箇所（R）を切り口にする。

- 切り口ごとに英語のクエリを 2〜4 本作る。食い違う知見を探すときは、反対の結果を表す語（`"no effect"`, `null`, `negative`, `heterogeneous` など）も使う。
- 採否の理由に ID を書く（例: `--reason "C2 支持: 同じ識別戦略で正の効果"`、`--reason "R3 原稿が引用"`、`--reason "足す候補: 雇用の減少を報告"`）。食い違う論文を、食い違うという理由で除外しない。
- **原稿がすでに引用している論文は登録する**（`./priorwork get` で書誌を確かめてから `./priorwork add <survey> <DOI>`）。原稿に `.bib` があれば（Octavo のプロジェクトなど）、`./priorwork add <survey> --cited` で、原稿が `[@key]` で引いている論文をまとめて登録できる（DOI の無いものは一覧に出るので、タイトルで探す）。`advice` では、引用の向きを確かめるためにすべて登録する。国内誌などで登録できないものは、3 章の表に「登録できず」と書く。

標準と手動では、カードの記入の前で止まり、Zotero に入れる DOI を示す（AGENTS.md「進め方」）。

## 6. カードを記入する

`priorwork-extract` の手順で記入する。さらに **原稿での役割**（`role`）を書く。

```bash
./priorwork card <survey> N --set "role=K2・C1 支持"
./priorwork card <survey> N --set "role=R2 原稿が引用; 向きが違う"
```

- `role`: 5 章の項目・4 章の主張・6 章の引用の ID と関係（支持 / 食い違い / 理論の出どころ / 方法の先例 / 背景、原稿が引用か足す候補か）。
- 4 章の文献の列を、カードに合わせて著者 (年) で埋める。文献が 1 本も無い主張が残ったら、その主張で検索を足す。それでも見つからなければ、主張を弱めるか削る案を 8 章か 9 章に書く。
- 原稿の主張に関わる論文（5 章で引く論文、6 章で向きを判定する論文）は、深さによらず本文で確かめる（本文確認済）。

## 7. レポートを書く

`<!-- 書く内容: … -->` に従う。引用するのはサーベイに採用した論文だけで、著者 (年) の表記は参照文献に合わせる。カードに書かれていないことを足さない。

**5 章 補完の一覧。** 原稿の順に、**原稿の言語で**書く。

- 見出しは `### K1 種類 — 節`。種類は「節を書く」（無い節・見出しだけの節）、「差し込む」（薄い節に段落を足す）、「引用を足す」（引用の無い主張・`[cite]`・`[@?]` に、引く論文と、引用を入れた文を示す）。
- 各項目に **場所**（節の見出しと、前か後の一文を原稿からそのまま引用）と **理由**（欠け・作者の印・主張の ID）を書き、その下に本文を書く。場所が無い項目は `./priorwork check` が WARN にする。
- **作者の印を先に埋める。** 一つ一つに、項目か、埋めない理由（文献で支えられない・範囲の外）を 3 章に書く。
- 補うのは文献で支える部分だけ。方法・結果の中身（データ・推定値・解釈）は書かない（方法の選び方を支える文献を示すのはよい）。原稿の書いてある部分と食い違うことを足すときは、その旨を理由に書く。
- 節をまるごと書くとき:
  - **イントロ**: 問題の重要性とパズル → 先行研究で分かっていないこと → この研究の問い・方法・主な結果・貢献。結果は 1 章の要約の範囲で書く。
  - **先行研究**: 研究の流れごとに、主張と根拠をまとめる。論文の列挙ではなく、流れの中で何が分かり何が残るかを書き、最後にこの研究の位置を示す。
  - **理論と仮説**: メカニズムと仮説を、仮説ごとに根拠の文献を添えて書く。対立する理論があれば、それが予測することも書く。

**食い違う先行研究を隠さない。** 原稿の結果と食い違う文献は本文で触れ、違いが生じうる理由（対象・時期・識別の違い）をカードの範囲で書く。**文献が言っていないことを文献のせいにしない。**

**6 章 引用の点検。** R ごとに、引かれた論文のカード（主な結果の**向き**・対象・方法）と原稿の書き方を比べて判定する（合う / 向きが違う / 言い過ぎ / 根拠が弱い）。合わないものは、どう直すか（言い方を弱める・別の論文に替える・食い違う知見も示す）を書く。

**7 章 足りない先行研究。** 研究の流れごとに、原稿のどこで、何のために引くとよいかを、採用論文を引いて書く。原稿の結果と食い違う知見を隠さない。

**8 章 仮説と文献。** 仮説ごとに、根拠の文献と食い違う文献、原稿での扱いを書く。

**9 章 論の組み立て。** 問い・空白・仮説・方法・結果・貢献のつながりへのコメント。先行研究から言えることと、原稿の主張を混ぜない。

**2 章 まず直すところ。** 最後に書く。大事な点を 3〜7 点、場所・問題・すること・根拠の文献とともに。直した文を勧めるときは、原稿の言語で短く示す。

## 8. 検査して書き出す

`priorwork-check` の手順で ERROR を 0 にしてから書き出す。

```bash
./priorwork export <survey> --draft          # reports/<名前>.draft.md（5 章と、引用した論文の参考文献）
./priorwork export <survey>                  # reports/<名前>.html（全体）
```

`--draft --format docx` で Word にもできる（pandoc が要る）。原稿が Octavo のプロジェクトにあれば、下の「Octavo のプロジェクトの原稿」の形で書き出す。

## Octavo のプロジェクトの原稿

- 下書きは、ほかの原稿と同じく「著者 (年)」で書く。Octavo の形への書き換えはエンジンがする:

  ```bash
  ./priorwork export <survey> --octavo    # <プロジェクト>/literature/priorwork/<サーベイ>.md と .json（引用は [@key]、参考文献の節は無い）
  ```

  キーは Octavo のプロジェクトの `.bib`（Zotero から書き出したもの）から DOI で引く。キーを自分で作らない。
- `.bib` に無い採用論文は `[@PRIORWORK:<DOI>]` と書かれ、DOI の一覧が出る。報告でその DOI をそのまま示し、「Zotero のコレクション（`./priorwork status` の「Octavo のプロジェクト」に出る名前）に入れ、Octavo のプロジェクトで `octavo bib pull` と `octavo priorwork resolve` を実行する」と伝える。resolve が印を `.bib` のキーに置き換える（それまで Octavo は「無いキー」として知らせる。Octavo 0.6.6 まででは、`octavo bib pull` の後にもう一度書き出す）。Priorwork が Zotero に書き込めるなら、`./priorwork zotero <survey> --add` で入れられる（AGENTS.md「Zotero」）。
- `./priorwork check` は、サーベイと Octavo の Zotero のコレクションが違うとき（WARN）、下書きが `.bib` に無い論文を引いているとき（WARN）を知らせる。コレクションが違えば、どちらに合わせるかをユーザーに聞く。
- 書き出したものは、Octavo のプロジェクトの受け取り場所（`literature/priorwork/`）に置かれる。原稿への取り込みは Octavo の側でする: ユーザーに、Octavo のプロジェクトのエージェントに「受け取った下書きを原稿に反映して」と頼むよう伝える。受け取り場所の外の Octavo のファイル（設定・`.bib`・原稿）は書き換えない。

- `export --octavo` は、5 章に続けて、2 章と 6〜9 章に書いたものを「著者へ」の部分として受け取り場所に置く（原稿の本文には入れない）。

## 9. 報告する

入口のスキル `priorwork` の「4. 終わったら報告する」に加えて、次を伝える。論文は著者 (年) で示す。

- 2 章の要点
- 欠けの地図の要点、足す項目の数と種類、作者の印のうち埋めたもの・埋めなかったもの（とその理由）
- 引用の点検で「向きが違う」「言い過ぎ」とした箇所の数
- 主張への文献の付き方（支える文献しかない主張・食い違う文献がある主張・文献が見つからなかった主張）
- 書き出したファイル（原稿へは、ユーザーが読んでから移すこと）
- Octavo のプロジェクトの原稿なら、受け取り場所に置いたファイルと、`.bib` に無かった論文の DOI（Zotero に入れて `octavo bib pull` すること）
