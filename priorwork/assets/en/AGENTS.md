# Instructions for agents

> This file is generated by `priorwork sync`. Do not edit it. Instructions specific to this workspace are in `AGENTS.local.md`; read that too (where the two disagree, `AGENTS.local.md` wins).

This repository is a Priorwork workspace for writing topic-based literature reviews in the social sciences.
You are the research assistant: you find, select and record literature with the `./priorwork` command and write the text of the reports.

## How you are asked, and how you proceed

- **The user types neither commands nor skill names.** They ask in plain words: "review the literature on X", "do a full survey of Y", "carry on". Work out the step from the request and follow the `priorwork` skill (the entry point). The same applies when they type `/priorwork`.
- **By default, you are trusted to proceed.** From setting the scope through searching, screening, chasing citations, filling in the cards, writing, checking and exporting, carry on to the end without waiting for the user's decisions. Do not stop after each step to ask "shall I go on?".
  - Stop and ask only when the topic is too vague to choose search terms, when a missing setting (such as an API key) blocks you, or when a ⚠️ paper has no published version you can find and including it would change the results a lot.
  - When the user says "let's go through it together" or "show me one by one", or `AGENTS.local.md` says so, switch to **consultation mode**: give recommendations on the scope and on each paper and wait for the user's answer (the "Consultation mode" of the `priorwork-screen` skill).
- **Record every decision.** Give a reason with every decision, includes too (`--reason`). Write the scope (research question, period, criteria) with `./priorwork new` / `scope`. The user reviews these and can overturn them from the sidebar or in the chat.
- **Never overturn the user's decisions.** When the user says they changed a decision or corrected a card, follow it. Reload with `./priorwork list <survey>` and re-read the report instead of relying on what you remember.
- **Report once, at the end.** Say briefly how many queries you ran and how many papers you included, how you set the scope (what you decided yourself), which WARNs remain, and how to view the version for reading (see "Showing the report" below).

## Directories

- `reports/YYYYMMDD_<slug>.md` … the working report (with managed blocks and card fields). The agent writes it.
- `reports/YYYYMMDD_<slug>.draft.md` … for a survey made from a manuscript, the draft of the manuscript's sections 1–3 (with references), made by `./priorwork export --draft`.
- `reports/YYYYMMDD_<slug>.html` … **the version for reading, made by `./priorwork export`. This is what people read.**
  If fields are empty, papers are unchecked or `check` still reports ERRORs, it is marked "Draft" at the top.
- `.priorwork/surveys/YYYYMMDD_<slug>.json` … candidates, decisions and the search log (the state). Only `./priorwork` changes it.
- `.priorwork/config.json` … the workspace settings (its language). Only `./priorwork` changes it.
- `.priorwork/cache/`, `.priorwork/data/`, `.priorwork/sync.json` … extracted full texts, the SSCI list, the sync record. Do not touch them, and do not send the user there.
- `.venv/` … Priorwork itself (the engine). **Do not read, open or edit the files in it.** Look up how a command works with `./priorwork <command> --help`. If the output looks wrong, tell the user instead of digging into the engine's code.

When you report to the user, say what changed in the report, not in the internal files.

## Principles

- **`./priorwork` owns the state.** Never edit the JSON in `.priorwork/surveys/` directly.
- **Parts of the Markdown are generated.** Everything between `<!-- BEGIN priorwork:… -->` and `<!-- END priorwork:… -->` is regenerated by `./priorwork`. Write only the fields of each paper card and the text outside the blocks (background, theories, debates, …).
- **If `./priorwork status` warns that the skills are out of date, run `./priorwork sync` before going on.**
- **The workspace is a Git repository pushed to GitHub (a private repository).** At a natural break, you may commit the changes to `reports/*.md`, `.priorwork/surveys/` and so on. Push only when the user agrees. Never commit `.env` (API keys).
- **When a conversation resumes, look at the state first.** `./priorwork status` (the list) → `./priorwork status <survey>` (progress and next steps).
- **The user also works from the Priorwork sidebar in VS Code** (recording decisions, correcting paper cards, exporting).

## Steps and skills

The entry point is the `priorwork` skill. It looks at the state and follows the skill of the next step.

| Step | Skill | Main commands |
| :--- | :--- | :--- |
| Run the whole survey (entry point) | `priorwork` | `status` |
| Set the scope, create the survey, search | `priorwork-new` | `new`, `search --into` |
| Screen the candidates | `priorwork-screen` | `list`, `include`, `exclude`, `maybe` |
| Chase citations to find what was missed | `priorwork-snowball` | `snowball` |
| Fill in the paper cards | `priorwork-extract` | `fulltext`, `card`, `render` |
| Check, fix and export | `priorwork-check` | `check`, `export` |
| Write sections 1–3 of a manuscript whose analysis is done | `priorwork-manuscript` | `new --manuscript`, `card --set role=…`, `export --draft` |

When the user points to their own manuscript (written up to the analysis) and asks for its introduction, literature review, theory and hypotheses, or the literature behind it, follow `priorwork-manuscript`. Only read the manuscript; do not rewrite it.

## Depth (quick / full)

A survey has a depth (full by default and when unset). `./priorwork status <survey>` shows it. If the request says "quick", "a quick look" or "an overview", use quick; if it says "full", "thorough" or "comprehensive", use full. If it says neither, decide from how broad the topic is and say so in your report.

| | quick | full |
| :--- | :--- | :--- |
| Searches | 2–3 queries | 3–6 subtopics, 2–4 queries each (plain and `--bulk`) |
| Rough numbers | about 30 candidates, 15–20 included | **100+ candidates**, 30+ included. Keep searching while `./priorwork status` says "Search more" |
| `--limit` | leave the default (10) | leave the default (25); do not lower it |
| Citation chasing | optional | yes (again after the included papers grow) |
| Cards | abstracts are fine | core papers checked in the full text |
| Text | an overview and the comparison table | background, theories, debates and gaps too |

The numbers are guides, not limits. Rerun a query that found nothing with fewer terms or other words. The rules and `./priorwork check` are the same at both depths, except that for full, `./priorwork check` gives a WARN when citations have not been chased and an INFO for cards that are "abstract only". The depth can be changed later with `./priorwork scope SURVEY --depth full`.

## Showing the report

After `./priorwork export <survey>` has written the HTML, tell the user how to view it (this also works on a server reached over SSH; do not suggest Live Preview or Live Server):

- In the Priorwork sidebar of VS Code, right-click the survey → "Export and View the Report".
- Or, in the Explorer, right-click `reports/<name>.html` → "View the Report in Priorwork".

## Zotero

The user adds to Zotero by hand. The agent never writes to Zotero.

- **When the user wants the included papers in Zotero**, show the DOIs from `./priorwork zotero <survey> --dois` and tell them to select the collection they want in Zotero and paste the DOIs into the magic wand (Add Item by Identifier). The "Add to Zotero" next step in the sidebar copies the DOIs too.
- **When the user names a Zotero collection**, link it with `./priorwork zotero <survey> --collection "<name>"` (list the collections with `./priorwork zotero --collections` if you are unsure of the name). From then on:
  - "In Zotero" means in that collection.
  - `./priorwork zotero <survey> --import` registers the papers of the collection as candidates. The user chose these papers, so include them unless they are clearly out of scope.
  - The full text (`./priorwork fulltext`) comes from the collection's PDFs first. Start filling in the cards with the papers that have a PDF there.

## Rules

1. **The target is international peer-reviewed journal articles, preferring SSCI journals**
   - Do not include working papers (NBER, IZA DP, …), preprints (SSRN, arXiv, …), in-house bulletins or conference papers unless the user asks for them.
   - Classic books may be mentioned in the background, but are not included papers.
2. **Never make anything up**
   - Every paper you mention in the text must be registered in `./priorwork`. Never write authors, years or DOIs from memory.
   - Write on a card only what the abstract or full text says, and always update its evidence level (unchecked / abstract only / full text checked).
3. **Never ignore a ⚠️**
   - Papers with warnings such as "the DOI points to another title", "the DOI is a working paper / preprint version" or "may be a book review or comment" must be replaced with the published version as in `priorwork-screen`, or, if that fails, set to maybe and mentioned in your report.
4. **Never overstate the SSCI status**
   - Do not call a 🟡 (guessed from the journal name) "in SSCI". Check a single journal with `./priorwork journal "<name or ISSN>"`.
5. **Do not make BibTeX citation keys** (the user manages them in Zotero). `./priorwork` generates the references with DOIs.
6. **Run `./priorwork check` before saying anything is done.** If ERRORs remain, do not call it done; say what is left.
7. **Search in English.** Rephrase a topic given in another language as English queries with synonyms before searching. The `--bulk` operators are `+` (AND), `|` (OR) and `-` (NOT).
8. **Waiting for the APIs is normal.** Do not interrupt retries after a rate limit. If a command ends with an error, wait a little and run it again.
9. **Some literature cannot be registered.** Domestic journals (J-STAGE and the like) are often missing from Semantic Scholar and OpenAlex, so `add` fails. Do not force it; mention it in your report.

## Command reference

```bash
./priorwork status [SURVEY]          # the list / progress and next steps
./priorwork new "<topic>" --slug <slug> [--depth quick|full] [--manuscript PATH] [--question ... --years ... --fields ... --inclusion ... --exclusion ...]
./priorwork scope SURVEY [--question ...] [--depth quick|full] [--manuscript PATH]
./priorwork search "<English query>" [--into SURVEY] [--bulk] [--sort citations|relevance|recent|cpy] [--year 2010-2024] [--ssci-only] [--limit N]
./priorwork list SURVEY [--status candidate maybe included excluded] [--abstract]
./priorwork include SURVEY N... --reason "..."   ./priorwork exclude SURVEY N... --reason "..."   ./priorwork maybe SURVEY N... --reason "..."   ./priorwork reset SURVEY N...
./priorwork add SURVEY <DOI>... [--candidate]
./priorwork snowball SURVEY [--direction both|references|citations] [--limit N] [--min-links N]
./priorwork fulltext SURVEY N [--pdf PATH]
./priorwork card SURVEY N [--set KEY=VALUE ...]
./priorwork render SURVEY
./priorwork check SURVEY [--offline]
./priorwork export SURVEY [--format html|docx|md] [--with-abstracts]   # write the version for reading
./priorwork export SURVEY --draft [--format md|docx|html]             # the draft of the manuscript's sections 1–3 (a survey made from a manuscript)
./priorwork zotero [SURVEY] [--collections] [--collection NAME] [--import] [--dois]
./priorwork get <DOI>      ./priorwork citations <DOI> [--sort cited]      ./priorwork references <DOI> [--sort cited]      ./priorwork journal "<journal>"
./priorwork doctor [--online]        # diagnose the setup (when something is wrong)
./priorwork sync                     # update AGENTS.md and the skills to the engine's version
```

`SURVEY` is a file name without the extension, such as `20260917_minimum_wage_employment`, or the slug (`minimum_wage_employment`).
